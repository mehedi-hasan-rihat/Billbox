# BillBox

A personal bill inbox and management Engine. BillBox gives every user a unique BillBox ID to receive bills from others, create bills manually, track payment lifecycle, manage recurring bills, and maintain a full audit trail — all in one place.

---

## The Problem

Bills are scattered across email attachments, phone galleries, WhatsApp chats, paper receipts, and provider websites. Simple questions become hard:

- Which bills are unpaid?
- Which bill's deadline is approaching?
- Which bill is overdue?
- Where is last month's electricity bill?

BillBox consolidates everything into a single personal bill inbox with lifecycle tracking.

## Features

### Identity & Auth
Every user gets a unique **BillBox ID** (`BB-XXXX-XXXX-XXXX`) at registration. JWT-based authentication with bcrypt password hashing. All data is strictly scoped to the authenticated user — no cross-user data leaks.

### Bill Inbox
Another BillBox user can send a bill directly to your BillBox ID. The bill lands in your inbox with `status = INBOX`. You review it, optionally correct details (name, category, due date), and confirm it. On confirmation the bill enters the normal payment lifecycle.

### Manual Bill Creation
Create bills yourself — restaurant receipts, utility bills, shopping records. Set the initial status as `UNPAID` or `PAID`. Attach a biller from your biller list. Set a due date, bill date, notes, and payment info.

### Bill Lifecycle & Smart Status
Bills move through a clear lifecycle:

```
INBOX → UNPAID → PAID
```

The API adds two computed states on top — derived from `status + dueDate` at query time, never stored:

| Status | Meaning |
|--------|---------|
| `INBOX` | In inbox, awaiting confirmation |
| `UNPAID` | Confirmed, no due date set |
| `UPCOMING` | Unpaid, due date is in the future |
| `DUE_TODAY` | Unpaid, due date is today |
| `OVERDUE` | Unpaid, due date has passed |
| `PAID` | Payment completed |

This means `UPCOMING`, `DUE_TODAY`, and `OVERDUE` are always accurate — no background job needed to keep them current.

### Billers
A personal contact list of bill senders/providers. A biller can be a BillBox user (linked by BillBox ID) or an external party (name, phone, email). Bills can be linked to a biller. Use `GET /billers/lookup?billBoxId=` to resolve a BillBox user before creating a biller.

### Payment Records
When marking a bill as paid, record: paid date, paid amount, payment method (`CASH`, `BKASH`, `NAGAD`, `BANK`, `CARD`, `OTHER`), and a payment reference/transaction ID. Payment metadata can be updated after the fact.

### Bill Event Timeline
Every bill has a full audit trail. Every significant action is recorded:

| Event | When |
|-------|------|
| `CREATED` | Bill created manually |
| `SENT` | Bill sent to a BillBox ID |
| `RECEIVED` | Bill landed in recipient's inbox |
| `CONFIRMED` | Inbox bill confirmed by recipient |
| `PAID` | Bill marked as paid |
| `EDITED` | Bill details edited |
| `NOTE_ADDED` | Note added or updated |
| `PAYMENT_UPDATED` | Payment record updated |
| `RECURRING_GENERATED` | Bill generated by a recurring rule |

### Recurring Bills
Set up a recurring rule for any bill that repeats — monthly Internet, weekly subscriptions, yearly renewals. The scheduler runs daily and generates bills automatically, a configurable number of days before the due date (default: 5 days), so the bill appears as `UPCOMING` when it's created. Generated bills are fully independent — paying one doesn't affect others.

Supported frequencies: `WEEKLY`, `MONTHLY`, `YEARLY`. Rules can be paused, resumed, or stopped.

### Search, Filter & Pagination
`GET /bills` supports composable filtering:
- Full-text search across bill name and biller name
- Filter by category, status (including computed states), source, type, date ranges
- Sort by bill date, due date, amount, or created date
- Cursor-stable pagination with `page` / `limit` and total metadata

All filtering is done in the database — no in-memory collection loading.

### Bill Notes
Attach free-text notes to any bill. Notes can be added, updated, or cleared.

## API Reference

Base URL: `http://localhost:3000/api/v1/`

All routes (except auth) require `Authorization: Bearer <token>`.

| Module | Base Path | Docs |
|--------|-----------|------|
| Auth | `/auth` | [docs/api/auth.md](docs/api/auth.md) |
| Bills | `/bills` | [docs/api/bills.md](docs/api/bills.md) |
| Inbox | `/inbox` | [docs/api/inbox.md](docs/api/inbox.md) |
| Billers | `/billers` | [docs/api/billers.md](docs/api/billers.md) |
| Recurring | `/recurring` | [docs/api/recurring.md](docs/api/recurring.md) |

### Response Format

All responses are wrapped by `TransformInterceptor`:

```json
{
  "success": true,
  "data": { ... },
  "timestamp": "2026-10-05T08:00:00.000Z"
}
```

### Error Format

All errors are handled by `AllExceptionsFilter`:

```json
{
  "statusCode": 404,
  "message": "Bill not found",
  "error": "Not Found",
  "timestamp": "2026-10-05T08:00:00.000Z",
  "path": "/api/v1/bills/clx..."
}
```

## Getting Started

```bash
# Install dependencies
npm install

# Set up environment variables (see below)
cp .env.example .env

# Run database migrations and generate Prisma client
npx prisma migrate dev --name init

# Start development server
npm run start:dev
```
